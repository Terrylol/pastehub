## Context

现有应用以 H2 作为默认数据源，Compose 已定义 MySQL 与 Redis 但尚未用于应用运行。图片上传已验证浏览器端到端流程；本变更聚焦其公开运行所需的持久化和匿名写入保护，详见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 让 MySQL 成为生产配置的投递元数据存储，并提供可重复启动的本地依赖环境。
- 用 Redis 实现原子、跨实例的 IP 固定窗口限流。
- 保持读取和取件码解析无额外限流，避免影响接收者正常取件。
- 所有阈值、窗口、可信代理与连接配置均可由环境变量覆盖。

**Non-Goals:**

- 不增加账号、验证码、风控画像或全局 WAF。
- 不为存量 H2 临时数据做迁移；开发数据库可重新创建。
- 不引入 Redis 持久化队列或分布式任务调度。

## Decisions

### MySQL 使用独立生产配置

默认开发/测试可继续使用 H2，以保持快速反馈；`prod` 配置必须从环境变量读取 MySQL 主机、数据库、账户和密码，并运行既有 Flyway 迁移。Compose 为 MySQL 提供命名卷和健康检查，应用启动依赖连接可用。

备选方案是在所有环境都强制 MySQL。该方案更接近生产，但会提高测试和本地开发门槛，因此不采用。

### Redis 固定窗口计数限流

每个受保护的动作按 `动作名 + 规范化客户端 IP + 时间窗口` 建立 Redis 键，使用原子自增并设置一次 TTL。默认值为：文本创建 10 次/分钟、图片初始化 10 次/分钟、图片发布 20 次/分钟、删除 20 次/分钟；配置可覆盖。超限时返回 `429`、`RATE_LIMITED` 与按当前窗口计算的 `Retry-After`。

固定窗口足以覆盖首发防滥用，依赖少且容易观测。令牌桶或滑动窗口能提供更平滑的体验，但增加 Lua 脚本或额外依赖，暂不采用。

### 客户端 IP 解析遵循可信代理边界

仅当请求来源命中显式配置的可信反向代理网段时，才解析 `X-Forwarded-For` 的首个地址；否则使用直连地址。这样避免公网调用方伪造 IP 绕过限制。

### Redis 不可用时拒绝匿名写入

限流依赖不可用时，受保护写入接口返回 `503`，不执行状态变更。匿名公开服务采用 fail-closed，避免 Redis 故障变成无限制写入窗口。

## Risks / Trade-offs

- [固定窗口边界可发生短时突发] → 保守阈值、按动作分组，并保留后续替换算法的配置边界。
- [同一 NAT 下多个正常用户共享配额] → 默认阈值面向普通使用场景，运维可按实际流量调整。
- [可信代理配置错误导致误判 IP] → 默认不信任转发头，并在部署文档中给出反向代理示例。
- [Redis 故障阻止写入] → 健康检查暴露 Redis 状态，运维恢复后请求自动继续。

## Migration Plan

1. 为 MySQL、Redis 和应用配置增加环境变量与健康检查，并在隔离环境启动依赖。
2. 使用 Flyway 在 MySQL 建立投递表；通过创建、重启、读取验证持久化。
3. 部署 Redis 限流，先以默认阈值启用并监测 429 与 503 指标。
4. 回滚时先移除应用对限流组件的调用，再回退运行时配置；MySQL 表由 Flyway 保留，不删除数据。
